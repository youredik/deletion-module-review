# Code Review: модуль `Deletion`

Ревью по присланному архиву. Часть выводов проверена запуском: под модуль поднят
PHP 8.5 + Doctrine ORM 2.19 + PHPUnit 11, написаны тесты (часть 2 задания).
Пункты с пометкой **[проверено]** воспроизведены кодом, а не выведены из чтения.

---

## Коротко

Идея хорошая: декларативные связи через атрибуты, разделение «удалить ребёнка» и
«разорвать связь», middleware-хуки, dry-run, транзакция. Но между документацией и
кодом расходится сама семантика связей, а в оркестраторе есть дефекты, при которых
данные удаляются в обход проверок.

Что чинил бы в первую очередь:

| # | Проблема | Последствие |
|---|---|---|
| 1 | Doctrine-прокси ломает поиск зависимостей **[проверено]** | удаление вопреки блокирующим связям |
| 2 | `execute()` не смотрит на `canDelete` | оркестратор удалит то, что проверка запретила |
| 3 | Нет защиты от циклов в `buildRecursive()` | бесконечная рекурсия, падение процесса |
| 4 | Порядок в «OrderedPlan» не топологический | нарушение внешних ключей при удалении |
| 5 | Ветка many-to-many для родителей не работает **[проверено]** | исключение на любом вызове |
| 6 | README и код описывают противоположную семантику `BLOCKING` | связи размечают не так, как они работают |

---

## 1. Критичные дефекты

### 1.1. Lazy-loaded сущность (прокси) теряет все зависимости **[проверено]**

`DeletionService.php:113` и `:252` берут класс через `$object::class`. У прокси Doctrine
это `Proxies\__CG__\App\Entity\Order`, а карта в `ensureMap()` построена по настоящим
именам классов. Совпадения нет — зависимости не находятся, `canDelete` возвращает `true`.

Прокси приезжает штатно: `$em->getReference()`, ленивая связь, `findOneBy` по другой
сущности. То есть один и тот же объект даёт разный ответ в зависимости от того, как его
загрузили. Тест `testProxyEntitySilentlyLosesAllChildren` фиксирует: блокирующий ребёнок
есть, а `canDelete = true` и `dependents` пуст.

Чинится в одну строку — резолвить настоящий класс:

```php
$class = $this->em->getClassMetadata($object::class)->getName();
```

Здесь же и корень проблемы: реальный класс вычисляется в трёх местах по-разному
(`$object::class`, `new ReflectionClass($object)`, `$this->em->getClassMetadata(...)`).
Нужен один приватный метод, и все — через него.

### 1.2. `execute()` игнорирует результат проверки

`DeletionOrchestrator.php:30-31`: `plan()` возвращает `RelationsDto` с полем `canDelete`,
но оно нигде не читается — сразу строится план и выполняется удаление. Единственная
защита от удаления заблокированной сущности — дисциплина вызывающего кода.

Ожидаемо: `execute()` сам проверяет `canDelete` и бросает доменное исключение
(`DeletionBlockedException` со списком блокирующих групп), либо принимает явный
флаг `force: true`. Инвариант должен жить в модуле, а не в вызывающем контроллере.

### 1.3. Бесконечная рекурсия на циклических связях

`DeletionOrchestrator.php:111-140`. `buildRecursive()` спускается в каждого потомка без
множества посещённых узлов. Цикл `A → B → A` (или самоссылающаяся сущность вроде дерева
категорий) уводит в бесконечную рекурсию — процесс падает по памяти или по стеку.
`$deleteMap` дедуплицирует только итоговый список, но не саму рекурсию: даже без цикла,
если узел достижим двумя путями, поддерево обходится повторно.

Нужен `visited` по паре `(class, id)`, и вход в рекурсию только для новых узлов.

### 1.4. План удаления не упорядочен

`DeletionOrchestrator.php:76-80` разворачивает `$deleteMap` в порядке добавления классов.
А добавляются они сверху вниз: сначала потомки первого уровня, потом — при рекурсии —
второго. Значит и удаляются они в том же порядке: родительские строки раньше своих
дочерних. При `ON DELETE RESTRICT` это нарушение внешнего ключа, при отсутствии
ограничений — осиротевшие строки.

DTO называется `OrderedPlanDto`, но сортировки в нём нет. Нужна топологическая:
собрать граф классов и удалять с листьев, либо считать глубину при обходе и
удалять по убыванию глубины.

### 1.5. Связи через промежуточную таблицу для родителей не работают **[проверено]**

`DeletionService.php:215-222` строит **DQL**, подставляя в `FROM` имя таблицы, а в
`SELECT` — имя колонки:

```php
$qb->select("jt.{$joinColumn}")->from($joinTable, 'jt')
```

DQL оперирует сущностями и полями, а не таблицами и колонками. Проверил на живом ORM:

```
Doctrine\ORM\Query\QueryException
[Semantical Error] line 0, col 24 near 'order_tag jt': Error: Class 'order_tag' is not defined.
```

То есть путь падает всегда — значит, он не покрыт ни тестами, ни реальным использованием.
Здесь нужен нативный SQL через DBAL, как это уже сделано в
`DeletionOrchestrator::detachJoinRow()`:

```php
$this->em->getConnection()->fetchFirstColumn(
    sprintf('SELECT %s FROM %s WHERE %s = ?', $joinColumn, $joinTable, $inverseJoinColumn),
    [$objectId]
);
```

### 1.6. `deleteByIds()` смешивает идентификаторы, если ключ не `id`

`DeletionOrchestrator.php:112-118`:

```php
$idField = 'id';
if (!in_array('id', $identifiers)) {
    $idField = $group->field;
}
```

`$group->field` — это поле связи ребёнка на родителя (например `order_id`), а `$group->ids`
— идентификаторы самих детей, полученные из `finder->getId()`. В итоге `deleteByIds()`
выполняет `DELETE ... WHERE e.order_id IN (:childIds)`: чужое пространство идентификаторов.
Удалятся не те строки либо ни одной. Для составных ключей ветка не работает в принципе —
`$identifiers` вернёт несколько полей, а обрабатывается один.

Брать надо настоящий идентификатор из метаданных, а составные ключи — либо поддержать
явно, либо честно отвергать с понятным исключением.

### 1.7. Ошибки middleware проглатываются молча

`DeletionOrchestrator.php:156-166`:

```php
try { $mw->{$method}(...$args); } catch (Throwable) {}
```

Пустой `catch` без логирования. Если middleware пишет аудит удаления и упал — удаление
всё равно пройдёт, а следа не останется. Для аудита это означает, что гарантий нет вообще.

Разумнее разделить: middleware, чья ошибка не критична (метрики, логи), и критичные
(аудит, интеграции). Первые — ловить и **логировать**, вторые — пропускать наружу, отменяя
транзакцию. Как минимум — не терять исключение.

Там же: `supports()` объявлен в интерфейсе, но **не вызывается ни разу**. Любая
реализация обязана его написать, и он ни на что не влияет — ловушка при добавлении
нового middleware. И `method_exists()` избыточен: интерфейс уже требует все методы,
зато опечатка в имени события молча ничего не сделает.

## 2. Семантика и документация

### 2.1. README и код описывают связь противоположно

README:

> `OrderItemEntity` нельзя удалить, если она связана с `OrderEntity`.
> `OrderEntity` можно удалить свободно.

Код (`DeletionService.php:120-122`):

```php
// BLOCKING на дочерней сущности означает "нельзя удалить РОДИТЕЛЯ", а не саму дочернюю
$isBlocking = false;
```

Это ровно наоборот. Реализовано второе: `findChildrenByAttributes()` переносит
`BLOCKING` в блокировку **родителя**. Пока это расхождение не снято, разработчики
размечают сущности по README и получают не ту защиту, которую ожидали, — причём
молча, без ошибки.

Здесь нужно определиться и зафиксировать в тесте. Мне ближе вариант из кода
(«нельзя удалить то, на что ссылаются»), тогда правки — в README и в названии:
`BLOCKING` → что-то вроде `RESTRICTS_PARENT`, чтобы направление читалось из имени.

### 2.2. Проверка блокирующих родителей — мёртвый код **[проверено]**

`DeletionService.php:122` жёстко ставит `$isBlocking = false`, поэтому цикл в
`analyze():47-52` (`hasHardParent`) не может сработать никогда. При этом ради этих
всегда-неблокирующих групп выполняются запросы, в том числе в промежуточные таблицы.

### 2.3. Связь `REFERENCE` + `cascade: NONE` молча исчезает **[проверено]**

`DeletionService.php:283-293`: группа попадает в результат, только если каскад
`delete`/`detach` либо связь блокирующая. Иначе — не попадает никуда, хотя записи есть.
Потребитель API не узнает, что на сущность кто-то ссылается. Либо это должно попадать в
отдельный список «просто ссылаются», либо поведение стоит описать явно.

### 2.4. Флаг `hard` в ответе не означает «блокирует» **[проверено]**

`canDelete()` склеивает три разных списка в один `dependents`. У detach-группы `hard` может
быть `true`, но удаление при этом разрешено; у родительских групп `hard` всегда `false`.
README же предлагает печатать по `hard` строку «(блокирует удаление)» — она будет врать.

Правильнее отдавать наружу структурированный ответ (`blocking` / `willBeDeleted` /
`willBeDetached`), а не плоский список с неоднозначным флагом.

### 2.5. README описывает несуществующий атрибут

В разделе 3 документирован атрибут `DependsOn` с параметром `parent`; в коде —
`RelationTo` с параметром `entity`. Параметр `cascade`, который реально управляет
поведением, в README не описан вовсе, а `type` не описан в списке параметров.

## 3. Надёжность и краевые случаи

**3.1. Поле-ассоциация роняет проверку [проверено].** `getScalarFkValue()`
(`DeletionService.php:227-239`) объявлен как `int|string|null`, но читает свойство как
есть. Если поле — настоящая ассоциация (`private OrderEntity $order`, ровно как в примере
README), возвращается объект и вылетает `TypeError`. Нужно распознавать ассоциацию по
метаданным и брать идентификатор через `getIdentifierValues()`.

**3.2. Неинициализированное типизированное свойство роняет проверку [проверено].**
Там же: нет `isInitialized()`. Для нового, ещё не заполненного объекта — фатальная ошибка
вместо ответа.

**3.3. Составные ключи не поддержаны.** `DeletionOrchestrator.php:92-93` берёт
`array_values($parentIdArr)[0]` — молча теряет вторую часть ключа. Лучше явное исключение,
чем тихо неверный `parentId` в `DELETE`.

**3.4. `IN (...)` без разбиения на пачки.** `deleteByIds()` и `detachJoinRow()` кладут в
запрос все идентификаторы разом. На большом наборе — упор в лимит параметров
(PostgreSQL — 65535) или в максимальный размер пакета. Нужны чанки по 1000–5000.

**3.5. Массовое удаление в обход UnitOfWork.** `deleteByIds()` выполняет DQL `DELETE`:
события жизненного цикла (`preRemove`/`postRemove`) не срабатывают, identity map не
чистится. Если на этих событиях висит очистка файлов, инвалидация кэша или переиндексация
— она не отработает, а `flush()` после этого может обращаться к уже удалённым строкам.
Как минимум это должно быть в README крупными буквами.

**3.6. Гонка между проверкой и удалением.** Между `plan()` и фактическим `DELETE` другой
запрос может создать новую блокирующую запись — она молча осиротеет. Нужна либо
блокировка родителя (`SELECT ... FOR UPDATE`) в той же транзакции, либо честная опора на
внешние ключи в БД.

**3.7. `isJsonField()` сломается на Doctrine ORM 3.** `DeletionService.php:317-325` читает
`$metadata->fieldMappings[$field]['type']` как массив; в ORM 3 это объект `FieldMapping`.
Плюс `options['json']` — не стандартная опция Doctrine. Надёжнее
`$metadata->getTypeOfField($field) === Types::JSON`.

**3.8. `setAccessible()` устарел в PHP 8.5 [проверено].** `DeletionService.php:235` —
прогон тестов выдаёт deprecation. С PHP 8.1 вызов не нужен, строку можно просто убрать.

**3.9. `array_filter()` ломает список.** `getJsonArrayParentIds():198` сохраняет исходные
ключи, поэтому массив перестаёт быть списком — при `json_encode` (а README отдаёт
`dependents` прямо в `JsonResponse`) вместо массива уедет объект. Нужен `array_values()`.

**3.10. Идентификаторы таблиц подставляются в SQL строкой.** `detachJoinRow():172` — без
экранирования. Источник — атрибуты в коде, не пользовательский ввод, поэтому инъекции
здесь нет, но на зарезервированном слове или имени в другом регистре запрос сломается.
Стоит прогонять через `quoteIdentifier()` платформы.

**3.11. Утечка чужих идентификаторов.** В ответе отдаются `ids` зависимых записей, а
запросы в `finder` ничем не ограничены по арендатору/владельцу. В многопользовательской
системе через `canDelete` можно собирать идентификаторы чужих записей. Стоит либо не
отдавать `ids` наружу, либо фильтровать по контексту доступа.

## 4. Производительность

**4.1. Полная гидрация сущностей ради счётчика и идентификаторов.**
`DeletionService.php:260-281` тянет через `finder` целые объекты, чтобы взять из них
только `id` и посчитать количество. У родителя со 100 тысячами детей это 100 тысяч
объектов в память на каждый вызов `canDelete()`. Нужен скалярный запрос:
`COUNT(*)` для счётчика и `SELECT id ... LIMIT N` для примеров. Тем более что README
обещает показывать «ID первых 5 записей» — значит, все они и не нужны.

**4.2. N+1 в рекурсии.** `DeletionOrchestrator.php:124-139` делает `find()` **на каждый
идентификатор** отдельно, и для каждого потомка заново вызывает `analyze()` — а тот, в
свою очередь, снова ходит в базу за родителями и детьми. На дереве в тысячу узлов это
тысячи запросов. Нужна пакетная загрузка (`findBy(['id' => $ids])`) и переиспользование
уже посчитанного анализа.

**4.3. Лишняя работа при обходе.** Оркестратору нужны только дети, но `analyze()` каждый
раз считает ещё и родителей — включая запросы в промежуточные таблицы (те самые, что
падают, п. 1.5). Стоит разделить на два метода.

**4.4. `getAllMetadata()` на первом обращении.** `DeletionService.php:82` заставляет
Doctrine разобрать метаданные **всех** сущностей проекта — заметная задержка первого
запроса, и любая поломанная маппинг-конфигурация в неродственном модуле уронит
`canDelete()`.

**4.5. Карта не кэшируется между запросами.** Она статична (зависит только от кода), но
строится заново на каждый процесс. Правильнее собирать её на этапе компиляции контейнера
(compiler pass) либо класть в PSR-6 кэш и прогревать вместе с остальным кэшем.

## 5. Архитектура, SOLID, PSR

**5.1. `DeletionService` совмещает пять ролей** — сканирование атрибутов, работа с
метаданными, чтение значений через рефлексию, разбор JSON и принятие решения «можно ли
удалять». Отсюда и сложность тестирования. Разделил бы на:
`RelationMapBuilder` (кэшируемый), `RelationValueReader`, `DependencyCounter`,
`DeletionPolicy` (решение). Каждый тестируется отдельно.

**5.2. Зависимость от конкретного класса, а не от интерфейса.** Конструктор требует
`GenericReadRepository`. В тестах его нельзя подменить штатно, поэтому в этой работе
пришлось наследоваться от заглушки. Нужен `ReadRepositoryInterface` — и тесты, и замена
реализации становятся тривиальными.

**5.3. Позиционные кортежи вместо объекта.** Карта хранит массивы из семи элементов и
распаковывается через `[$childClass, $field, $hard, $joinTable, ...]` в двух местах.
Читается тяжело, при добавлении поля надо не забыть все точки распаковки — а в docblock
`DeletionService.php:17` тип для последнего элемента уже указан неверно (`?string` вместо
значения enum). Просится `final readonly class RelationRule`.

Заодно `getChildRelationRules()` — публичный метод, отдающий наружу внутреннее
представление карты; оркестратор распаковывает чужие кортежи. Возвращать надо объекты.

**5.4. Интерфейс middleware слишком широкий.** Шесть обязательных методов: реализация,
которой нужны два события, вынуждена писать четыре пустых. Плюс мёртвый `supports()` и
нетипизированный `array $relation`. Здесь лучше одно событие-объект
(`handle(DeletionEvent $event)`) либо базовый класс с пустыми реализациями.

**5.5. Middleware выполняются внутри транзакции.** Любой поход по сети из middleware
удерживает открытую транзакцию всё время ответа. Для метрик и уведомлений разумнее
копить в памяти и отправлять после коммита.

**5.6. Атрибут на классе + имя поля строкой.** Опечатка в `field` обнаружится только в
рантайме и приведёт к «зависимостей нет» — то есть к разрешённому удалению. Безопаснее
вешать атрибут на само свойство (`TARGET_PROPERTY`): имя поля тогда не дублируется, и
переименование через IDE ничего не ломает. Как минимум нужна проверка при сборке карты:
поле существует и является ассоциацией/скаляром/JSON.

**5.7. `execute()` ничего не возвращает.** Вызывающий код не знает, что удалено. Для
аудита и для ответа API нужен отчёт: сколько строк каких классов удалено и разорвано.

**5.8. `dryRun` дёргает middleware как при настоящем удалении.** Middleware, пишущий
аудит, зафиксирует удаление, которого не было. Флаг стоит передавать в событие.

**5.9. Мелочи по PSR-12.** Открывающая скобка тела после многострочного списка
аргументов должна стоять на строке закрывающей круглой (`) {`) — сейчас переносится
(`DeletionService.php:24-26` и другие конструкторы). `if (...) return $g;` без фигурных
скобок (`DeletionOrchestrator.php:150`). Сбитый отступ на `DeletionService.php:261`.
Ошибочный `@return DependentGroupDto[]` у метода, возвращающего пару списков
(`DeletionService.php:246`), и склеенные строки в docblock `OrderedPlanDto`.

## 6. Что хорошо

- Декларативная разметка атрибутами вместо конфигурации — правильный выбор, читается
  рядом с сущностью.
- Разделение «удалить ребёнка» и «разорвать связь» — редко встречается, а нужно почти
  всегда.
- Иммутабельные DTO, `declare(strict_types=1)`, enum вместо строковых констант.
- `dryRun` и middleware-хуки заложены сразу — это то, чего обычно не хватает.
- Всё удаление обёрнуто в одну транзакцию.

---

## 7. Что сделал бы иначе, если строить заново

1. Карта связей компилируется один раз в контейнере, отдаётся как готовый набор
   объектов `RelationRule`; при сборке валидируется (поле существует, класс — сущность).
2. Реальный класс сущности определяется в одном месте.
3. `analyze()` не тянет объекты: `COUNT(*)` для решения, идентификаторы — отдельным
   скалярным запросом с лимитом и только когда нужны.
4. Обход графа — итеративный, с множеством посещённых узлов и топологической
   сортировкой на выходе; удаление пачками с листьев.
5. `execute()` проверяет `canDelete` сам и возвращает отчёт.
6. Middleware получает одно типизированное событие; ошибки некритичных логируются,
   критичных — валят транзакцию; отправка наружу — после коммита.
7. Публичный контракт отдаёт три раздельных списка вместо плоского с флагом `hard`.

## 8. Часть 2 — тесты

Написаны PHPUnit-тесты для `DeletionService`: `tests/DeletionServiceTest.php`.

Разделены на две группы:

- **Зафиксированное поведение** — то, что работает верно и должно быть защищено от
  регрессий: блокирующий ребёнок запрещает удаление, `DETACH_RELATIONS` не запрещает,
  `DELETE_CHILD` попадает в список на удаление, счётчик совпадает с числом
  идентификаторов.
- **Найденные дефекты** — тесты, воспроизводящие проблемы из ревью: прокси (п. 1.1),
  потеря `REFERENCE`+`NONE` (2.3), мёртвая проверка родителей (2.2), неоднозначный `hard`
  (2.4), `TypeError` на поле-ассоциации (3.1), неинициализированное свойство (3.2).
  Они зелёные, потому что проверяют **фактическое** поведение; в каждом указано, каким
  оно должно быть. После исправлений эти тесты станут красными — и это ровно то место,
  где их нужно переписать под правильное поведение.

Запуск:

```bash
composer install
./vendor/bin/phpunit
```

Результат: `Tests: 11, Assertions: 27`, всё зелёное; одно предупреждение об устаревшем
`setAccessible()` приходит из самого модуля (п. 3.8).

Оговорка: `Shared\Persistence\GenericReadRepository` в архив не входит, а
`DeletionService` типизирует его в конструкторе — без него код не загружается. Поэтому в
`src/Shared/Persistence/` лежит заглушка, восстановленная по вызовам, а в тестах —
наследник от неё. Это и есть иллюстрация к п. 5.2.
