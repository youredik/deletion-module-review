# Code Review: модуль `Deletion`

Эдуард Сарваров · для 3snet

Под модуль поднято окружение (PHP 8.5, Doctrine ORM 2.19, PHPUnit 11), поэтому часть
выводов не выведена из чтения, а воспроизведена запуском — такие помечены
**[проверено]**, рядом приведён фактический вывод.

---

## Резюме

Идея модуля правильная: связи между сущностями описываются декларативно рядом с самими
сущностями, отдельно разведены «удалить потомка» и «разорвать связь», заложены dry-run,
хуки и общая транзакция. Такой модуль в системе с большой доменной моделью нужен.

Но у него есть свойство, которое перевешивает всё остальное: **при любой ошибке
конфигурации или неучтённом случае он разрешает удаление, а не запрещает.** Для
компонента, чья единственная задача — не дать удалить лишнее, это перевёрнутый выбор
по умолчанию. Ниже это разобрано первым пунктом, потому что из него растёт большинство
дефектов.

Второе по значимости — модуль строит собственную метамодель связей поверх той, что уже
есть в Doctrine, и дублирует её вручную. Отсюда и рассинхрон с маппингом, и неработающая
ветка many-to-many, и падения на полях-ассоциациях.

| # | Что | Последствие |
|---|---|---|
| 1 | Все режимы отказа разрешают удаление | защита не срабатывает молча |
| 2 | Прокси Doctrine теряет все связи **[проверено]** | `canDelete = true` при живых блокирующих потомках |
| 3 | `execute()` не проверяет `canDelete` | удаление в обход собственной проверки |
| 4 | Рекурсия без защиты от циклов | зависание и падение процесса |
| 5 | «Упорядоченный план» без сортировки | нарушение внешних ключей |
| 6 | Ветка many-to-many для родителей **[проверено]** | исключение на каждом вызове |
| 7 | README и код трактуют `BLOCKING` наоборот | связи размечают не тем, чем они работают |

---

## 1. Что сделано хорошо

Это стоит сказать прежде критики, потому что фундамент здравый.

- **Декларативность.** Правило удаления живёт рядом с сущностью, а не в конфиге и не в
  сервисе. Читается там, где и нужно.
- **Разделение `DELETE_CHILD` / `DETACH_RELATIONS`.** Различие между «удалить потомка» и
  «разорвать связь, потомка оставить» обычно всплывает поздно и дорого. Здесь оно
  заложено сразу и это правильно.
- **Заложены dry-run и точки расширения.** Возможность посмотреть план до выполнения —
  то, чего в таких модулях обычно нет.
- **Аккуратная база кода.** `declare(strict_types=1)`, `final`, `readonly` DTO, enum
  вместо строковых констант, внедрение через конструктор. Всё удаление обёрнуто в одну
  транзакцию.
- **Разделение анализа и исполнения** на два класса — направление верное, вопросы дальше
  только к тому, как проведена граница.

## 2. Архитектура

### 2.1. Модуль отказывает «в сторону разрешения»

Это главное замечание. Пройдёмся по всем режимам отказа:

| Что пошло не так | Что вернёт `canDelete()` |
|---|---|
| Сущность пришла как прокси **[проверено]** | `true`, зависимостей нет |
| `RelationTo` объявлен на абстрактном предке **[проверено]** | `true`, у наследников связей нет |
| Опечатка в FQCN в `entity:` | `true`, ключ карты никто не спросит |
| Опечатка в имени поля в `field:` | `true`, свойство не найдено — связи нет |
| Связь `REFERENCE` + `cascade: NONE` **[проверено]** | `true`, группа исчезает из ответа |
| Упал middleware | ошибка проглочена, удаление продолжается |
| Проверка блокирующих родителей **[проверено]** | недостижимый код, не сработает никогда |

Ни один из этих случаев не приводит к ошибке. Все — к разрешению удаления. Причём молча:
ни исключения, ни записи в лог. Модуль-страж обязан вести себя ровно наоборот: если он не
может достоверно ответить на вопрос «есть ли зависимости», он должен отказать и
пожаловаться, а не пропустить.

Архитектурно это лечится не заплатками в каждом месте, а переносом проверок на этап
сборки: карта связей строится и **валидируется при компиляции контейнера** (класс из
`entity:` существует и является сущностью, поле существует и его вид совпадает с
объявленным). Тогда опечатка — это красная сборка, а не тихо разрешённое удаление.
Оставшиеся рантайм-неопределённости (не удалось определить класс, неизвестный вид связи)
должны бросать доменное исключение.

### 2.2. Собственная метамодель дублирует то, что Doctrine уже знает

Атрибут `RelationTo` требует руками указать: целевой класс, имя поля, имя промежуточной
таблицы и обе её колонки. Всё это Doctrine уже хранит в маппинге. Проверил на живом ORM:

```
category   type=2 target=Tests\Doctrine\Category   joinTable=—
labels     type=8 target=Tests\Doctrine\Label      joinTable=product_label
```

То есть цель связи, её вид и промежуточная таблица доступны из
`ClassMetadata::getAssociationMappings()` без единой строчки ручного описания.

Последствия дублирования видны по всему модулю:

- **рассинхрон.** Никто не проверяет, что `field` вообще существует и что `joinTable`
  совпадает с маппингом. Переименовали поле — модуль молча перестал защищать (см. 2.1).
- **ручная работа с промежуточной таблицей**, которая написана с ошибкой и не работает
  вовсе (п. 3.5).
- **самодельное чтение значений через рефлексию**, которое падает на обычной ассоциации
  (п. 5.1), хотя у Doctrine для этого есть `getIdentifierValues()`.
- **проблема с прокси** (п. 3.1): её бы не было, если бы класс определялся через
  метаданные — `getClassMetadata()` сам приводит имя прокси к настоящему
  классу **[проверено]**.

Правильная граница: **Doctrine отвечает за структуру связей, атрибут — только за
политику.** То есть атрибут вешается на само свойство-ассоциацию и говорит лишь одно —
что делать при удалении:

```php
class OrderItemEntity
{
    #[OnDelete(OnDelete::RESTRICT)]
    private OrderEntity $order;

    #[OnDelete(OnDelete::CASCADE)]
    private ?ShipmentEntity $shipment;
}
```

Ни `field`, ни `joinTable`, ни колонок — всё берётся из маппинга. Опечатка в имени поля
становится невозможной, потому что имени поля больше нет. Переименование через IDE
переносит атрибут вместе со свойством.

### 2.3. Решение «можно ли удалять» принимается в двух местах и они разошлись

`DeletionService::analyze()` вычисляет `canDelete`. `DeletionOrchestrator::execute()`
(`DeletionOrchestrator.php:30`) вызывает `plan()`, получает тот же `RelationsDto` — и
**не смотрит на это поле вообще**, сразу строя план удаления.

Это не просто пропущенная строчка. Это следствие того, что политика не выделена в
отдельный элемент: она размазана между `analyze()` (решает) и `execute()` (обязан был
соблюсти, но не обязан по контракту). Пока инвариант не принадлежит никому конкретно,
его легко потерять — что и произошло.

Инвариант «нельзя удалять то, что заблокировано» должен жить внутри модуля и
обеспечиваться исполнителем, а не дисциплиной вызывающего кода.

### 2.4. План удаления не смоделирован

`OrderedPlanDto` — это два плоских массива, внутри которых ассоциативные массивы
(`['class' => ..., 'ids' => ..., 'field' => ...]`). В такой структуре нет ни узлов, ни
рёбер, ни глубины — то есть в ней **нечего сортировать**. Поэтому и порядок удаления
получается тем, в котором классы попали в массив (п. 3.4), а не тем, который требуется
внешним ключам.

Это ровно тот случай, когда отсутствие модели порождает баг: топологическую сортировку
невозможно приделать сбоку, для неё нужен граф. Нужны `PlanNode` (класс + набор
идентификаторов + глубина) и `PlanEdge`, и тогда сортировка становится отдельным
компонентом на 30 строк, который тестируется без базы данных вообще.

### 2.5. Чтение и запись не разделены

`canDelete()` — это запрос: «покажи, можно ли удалить». Он вызывается из контроллера,
скорее всего на каждый элемент списка, чтобы решить, показывать ли кнопку. Для ответа
достаточно `EXISTS`.

`execute()` — команда, ей нужны конкретные идентификаторы, чтобы их удалить.

Сейчас обе стороны ходят через одну и ту же функцию, которая **материализует все
зависимые сущности целиком** (п. 6.1). В результате дешёвый вопрос стоит как дорогая
операция. Разделение на «read side» (`EXISTS` для решения, выборка примеров только по
запросу) и «write side» (полные идентификаторы, пачками) убирает и проблему
производительности, и путаницу в контракте (п. 4.4).

### 2.6. То, что названо middleware, устроено как хуки — и от этого проблемы

Настоящий middleware оборачивает вызов и решает, передавать ли управление дальше — как в
Symfony Messenger: `handle($envelope, StackInterface $stack)`. Здесь же —
фиксированный набор точек «до/после», вызываемых так:

```php
// DeletionOrchestrator.php:156-166
private function notify(string $method, mixed ...$args): void
{
    foreach ($this->middlewares as $mw) {
        if (method_exists($mw, $method)) {
            try { $mw->{$method}(...$args); } catch (Throwable) {}
        }
    }
}
```

Что отсюда следует:

- **типов нет.** Вызов через строку и `...$args` не проверяется ни PHP, ни статическим
  анализатором. Ошибка в числе или порядке аргументов проявится только в рантайме,
  и — из-за пустого `catch` — вообще никак не проявится.
- **обернуть операцию нельзя.** Чтобы измерить длительность, наблюдателю приходится
  самому сшивать `before`/`after` и хранить состояние между вызовами. Настоящий
  middleware сделал бы это одним `try/finally`.
- **прервать операцию нельзя.** Проверка прав или бизнес-запрет здесь не реализуемы, хотя
  название обещает обратное.
- **`supports()` объявлен в интерфейсе, но не вызывается ни разу.** Каждая реализация
  обязана его написать, и он ни на что не влияет.
- **`method_exists()` избыточен** — интерфейс и так требует все методы; зато опечатка в
  имени события молча не сделает ничего.
- **всё выполняется внутри транзакции.** Поход по сети из наблюдателя держит транзакцию
  открытой; на MySQL это чужие блокировки и риск таймаута.

Нужно выбрать одно из двух и назвать честно: либо настоящая цепочка middleware (тогда
появляются и прерывание, и обёртка), либо типизированные события через штатный
`EventDispatcher` (тогда `#[AsEventListener]`, приоритеты, и никакой рефлексии).
Смешение даёт худшее от обоих.

### 2.7. Новый вид связи требует правки существующего кода

Виды связей разбираются цепочкой `if / elseif` в двух местах —
`findParentsByAttributes()` и `findChildrenByAttributes()`. Добавление любого нового вида
(полиморфная связь, связь через внешний сервис, мягкое удаление) означает правку обеих
цепочек. Это нарушение принципа открытости/закрытости в чистом виде, и именно здесь оно
дорого: ветки почти дублируют друг друга, и одна из них (many-to-many) уже разъехалась
настолько, что не работает.

Просится `RelationResolverInterface` с реализациями `ScalarFk`, `JoinTable`, `JsonArray`
и выбором по виду правила. Новый вид связи — новый класс и его тест, без касания
существующего кода.

### 2.8. У модуля нет границы

`DeletionService` одновременно и публичный API, и внутренняя механика. Метод
`getChildRelationRules()` (`DeletionService.php:306`) отдаёт наружу внутреннее
представление карты — массивы из семи элементов, — и оркестратор их распаковывает
позиционно. Любое изменение формата карты ломает соседа.

Наружу должны смотреть два узких контракта — «проверить» и «удалить», — а карта, правила
и способы чтения значений оставаться внутренностями модуля.

### 2.9. Модуль сопротивляется тестированию, и это архитектурный дефект

Показательно, что тестов нет вообще. Причины структурные, а не «не успели»:

- зависимость от **конкретного класса** `GenericReadRepository`, а не от интерфейса —
  подменить штатными средствами нельзя (в части 2 пришлось наследоваться);
- карта строится внутри сервиса из глобального состояния (`getAllMetadata()`), задать её
  снаружи нечем;
- чтение значений — самодельная рефлексия, зависящая от реальных объектов;
- решение, план и исполнение переплетены, поэтому проверить сортировку плана без базы
  данных невозможно.

Каждый из пунктов 2.1–2.8 при исправлении делает модуль тестируемым как побочный эффект.
Это хороший признак того, что правки те самые.

## 3. Критичные дефекты

### 3.1. Прокси Doctrine теряет все связи **[проверено]**

`DeletionService.php:113` и `:252` определяют класс через `$object::class`. У лениво
загруженной сущности это `Proxies\__CG__\App\Entity\Order`, а карта построена по
настоящим именам. Совпадения нет — связи не находятся.

Причина глубже, чем кажется: прокси — это **подкласс**, а атрибуты подклассом не
наследуются. Проверил:

```
атрибутов у подкласса: 0 (у родителя они есть)
```

Поэтому ломается не только поиск по карте, но и разбор атрибутов самого объекта.

Прокси приходит штатно: `getReference()`, ленивая связь, обращение через другую сущность.
То есть ответ модуля зависит от того, каким путём загрузили объект. Тест
`testProxyEntitySilentlyLosesAllChildren` фиксирует: блокирующий потомок есть,
`canDelete` возвращает `true`, список зависимостей пуст.

Исправление — определять класс через метаданные, они сами приводят прокси к настоящему
классу **[проверено]**:

```php
$class = $this->em->getClassMetadata($object::class)->getName();  // → App\Entity\Order
```

и делать это **в одном месте**: сейчас реальный класс вычисляется тремя разными
способами.

Тот же корень даёт вторую, менее заметную проблему: если `RelationTo` объявить на
абстрактной базовой сущности, наследники его не увидят — по той же причине.

### 3.2. `execute()` не проверяет `canDelete`

Разобрано в п. 2.3. Практически: оркестратор удалит сущность, для которой `canDelete()`
вернул `false`. Нужна проверка внутри `execute()` с доменным исключением, содержащим
список блокирующих групп, и явный флаг `force` для случаев, когда обойти проверку надо
осознанно.

### 3.3. Бесконечная рекурсия на циклах

`DeletionOrchestrator.php:111-140`. Спуск по потомкам идёт без множества посещённых узлов.
Цикл `A → B → A` или самоссылающаяся сущность (дерево категорий) уводят в бесконечную
рекурсию. `$deleteMap` дедуплицирует только итоговый список, но не сам обход: даже без
цикла, если узел достижим двумя путями, поддерево обходится повторно — на широком графе
это экспоненциальный рост.

Нужен `visited` по паре «класс + идентификатор» и вход в рекурсию только для новых узлов.
Обход лучше сделать итеративным — глубина дерева данных не должна упираться в стек PHP.

### 3.4. План удаления не упорядочен

`DeletionOrchestrator.php:76` разворачивает карту удаления в порядке добавления классов, а
добавляются они сверху вниз. Значит и удаляются сверху вниз: родительские строки раньше
своих дочерних. При `ON DELETE RESTRICT` — ошибка внешнего ключа, без ограничений —
осиротевшие строки. Нужна топологическая сортировка (см. 2.4).

### 3.5. Связи через промежуточную таблицу для родителей не работают **[проверено]**

`DeletionService.php:215-222` строит **DQL**, подставляя в `FROM` имя таблицы, а в
`SELECT` — имя колонки:

```php
$qb->select("jt.{$joinColumn}")->from($joinTable, 'jt')
```

DQL работает с сущностями и полями, а не с таблицами и колонками. Живой ORM:

```
Doctrine\ORM\Query\QueryException
[Semantical Error] line 0, col 24 near 'order_tag jt': Error: Class 'order_tag' is not defined.
```

Путь падает всегда — значит, он никогда не выполнялся ни в тестах, ни в проде. Здесь
нужен нативный SQL через DBAL, как это уже правильно сделано в
`DeletionOrchestrator::detachJoinRow()`. А ещё лучше — вовсе не хранить имена таблиц в
атрибуте и брать их из маппинга (п. 2.2).

### 3.6. `deleteByIds()` смешивает разные пространства идентификаторов

`DeletionOrchestrator.php:113-115`:

```php
$idField = 'id';
if (!in_array('id', $identifiers)) {
    $idField = $group->field;
}
```

`$group->field` — поле связи потомка на родителя, а `$group->ids` — идентификаторы самих
потомков. В итоге выполняется `DELETE ... WHERE e.order_id IN (:childIds)`: сравнение
внешнего ключа с чужими идентификаторами. Удалятся не те строки либо ни одной. Составные
ключи не поддержаны в принципе — `getIdentifier()` вернёт несколько полей, обрабатывается
одно (там же `:93` берёт `array_values(...)[0]`).

### 3.7. Ошибки наблюдателей исчезают

`DeletionOrchestrator.php:162` — пустой `catch (Throwable)`. Если middleware пишет аудит
удаления и упал, удаление всё равно произойдёт, а следа не останется. Для аудита это
означает отсутствие гарантий как таковых.

Нужно разделить критичных и некритичных наблюдателей: у первых исключение отменяет
транзакцию, у вторых — логируется. Терять его молча нельзя ни в одном из случаев.

## 4. Семантика и документация

### 4.1. README и код описывают связь противоположным образом

README:

> `OrderItemEntity` нельзя удалить, если она связана с `OrderEntity`.
> `OrderEntity` можно удалить свободно.

Код (`DeletionService.php:120-122`):

```php
// BLOCKING на дочерней сущности означает "нельзя удалить РОДИТЕЛЯ", а не саму дочернюю
$isBlocking = false;
```

Реализовано второе. Пока расхождение не снято, разработчик размечает сущности по
документации и получает не ту защиту — молча.

Мне ближе вариант из кода («нельзя удалить то, на что ссылаются» — это обычный
`RESTRICT`), тогда править нужно README и само имя: `BLOCKING` → `RESTRICT_PARENT` или
`PROTECTS_TARGET`, чтобы направление читалось из названия и такой вопрос больше не
возникал.

### 4.2. Проверка блокирующих родителей недостижима **[проверено]**

`DeletionService.php:122` жёстко ставит `$isBlocking = false`, поэтому цикл в
`analyze():47-52` не может сработать никогда. При этом запросы ради этих групп
выполняются — включая обращения в промежуточные таблицы, то есть в код из п. 3.5.

### 4.3. Связь `REFERENCE` + `cascade: NONE` исчезает из ответа **[проверено]**

`DeletionService.php:283-293`: группа попадает в результат, только если каскад
`delete`/`detach` либо связь блокирующая. Иначе — никуда, хотя записи существуют.
Потребитель не узнает, что на сущность кто-то ссылается.

### 4.4. Флаг `hard` в ответе не означает «блокирует» **[проверено]**

`canDelete()` склеивает три разных списка в один. У detach-группы `hard` бывает `true`,
но удаление при этом разрешено; у родительских групп `hard` всегда `false`. README же
предлагает печатать по этому флагу «(блокирует удаление)» — надпись будет неверной.

Наружу нужен структурированный ответ — `blocking` / `willBeDeleted` / `willBeDetached`, —
а не плоский список с неоднозначным флагом.

### 4.5. README описывает несуществующий атрибут

В разделе 3 документирован `DependsOn` с параметром `parent`; в коде — `RelationTo` с
параметром `entity`. Параметр `cascade`, который реально управляет поведением, не описан
вовсе, а `type` отсутствует в списке параметров.

## 5. Краевые случаи

**5.1. Поле-ассоциация роняет проверку [проверено].** `getScalarFkValue()`
(`DeletionService.php:227-239`) объявлен как `int|string|null`, но читает свойство как
есть. Если поле — настоящая ассоциация (`private OrderEntity $order`, ровно как в примере
README), возвращается объект и вылетает `TypeError`. Вид поля надо определять по
метаданным и брать идентификатор через `getIdentifierValues()`.

**5.2. Неинициализированное типизированное свойство роняет проверку [проверено].** Там же
нет `isInitialized()`: для нового, ещё не заполненного объекта — фатальная ошибка вместо
ответа.

**5.3. Массовое удаление в обход UnitOfWork.** `deleteByIds()` выполняет DQL `DELETE`:
события жизненного цикла (`preRemove`/`postRemove`) не срабатывают, identity map не
очищается. Если на этих событиях висит удаление файлов, инвалидация кэша или
переиндексация — она не отработает, а `flush()` после этого может обратиться к уже
удалённым строкам. То же касается строк в промежуточных таблицах у каскадно удалённых
потомков: они останутся сиротами, потому что план разрывает связи только для правил
самого корня.

**5.4. `IN (...)` без разбиения на пачки.** `deleteByIds()` и `detachJoinRow()` кладут в
запрос все идентификаторы разом — упор в лимит параметров или в размер пакета. Нужны
чанки.

**5.5. Гонка между проверкой и удалением.** Между `plan()` и `DELETE` другой запрос может
создать новую блокирующую запись. Нужна блокировка корня в той же транзакции
(`LockMode::PESSIMISTIC_WRITE`) либо честная опора на внешние ключи.

**5.6. `isJsonField()` сломается на Doctrine ORM 3.** `DeletionService.php:317-321` читает
`$metadata->fieldMappings[$field]['type']` как массив; в ORM 3 это объект `FieldMapping`.
Плюс `options['json']` — не стандартная опция. Надёжнее
`$metadata->getTypeOfField($field) === Types::JSON`.

**5.7. `setAccessible()` устарел в PHP 8.5 [проверено].** `DeletionService.php:180` и
`:235` — прогон тестов выдаёт предупреждение. С PHP 8.1 вызов не нужен.

**5.8. `array_filter()` ломает список.** `DeletionService.php:198` сохраняет исходные
ключи, массив перестаёт быть списком, и при сериализации (README отдаёт `dependents`
прямо в `JsonResponse`) вместо массива уедет объект. Нужен `array_values()`.

**5.9. Имена таблиц подставляются в SQL строкой.** `DeletionOrchestrator.php:172` — без
экранирования. Источник — атрибуты в коде, поэтому инъекции нет, но на зарезервированном
слове или имени в другом регистре запрос сломается. Нужен `quoteIdentifier()`.

**5.10. Утечка чужих идентификаторов.** Наружу отдаются `ids` зависимых записей, а
запросы ничем не ограничены по владельцу. В многопользовательской системе через
`canDelete` можно собирать идентификаторы чужих записей. Либо не отдавать `ids`, либо
фильтровать по контексту доступа.

## 6. Производительность

**6.1. Полная материализация сущностей ради счётчика.** `DeletionService.php:260-281`
загружает через `finder` целые объекты, чтобы взять только идентификаторы и посчитать
количество. У родителя со 100 тысячами потомков это 100 тысяч объектов в памяти на каждый
вызов `canDelete()` — а вызывается он, судя по README, из контроллера.

Для решения достаточно `EXISTS`, а это принципиально дешевле `COUNT(*)`: база
останавливается на первой найденной строке.

```sql
SELECT EXISTS(SELECT 1 FROM order_item WHERE order_id = ? LIMIT 1)
```

Идентификаторы примеров (README обещает «первые 5») — отдельным запросом с `LIMIT` и
только когда их правда просят.

**6.2. Скрытое требование к индексам.** Каждая проверка — это фильтр по внешнему ключу у
потомка. Если на `child.parent_id` нет индекса, на MySQL это полное сканирование таблицы
на каждый вызов. Модуль молча закладывается на индексы, которых может не быть; проверку
их наличия имеет смысл встроить в валидацию карты на этапе сборки.

**6.3. N+1 в рекурсии.** `DeletionOrchestrator.php:128` делает `find()` **на каждый
идентификатор** отдельно, и для каждого потомка заново вызывает `analyze()` (`:137`),
который снова ходит в базу. На дереве в тысячу узлов — тысячи запросов. Нужна пакетная
загрузка и переиспользование уже посчитанного.

**6.4. Лишняя работа при обходе.** Оркестратору нужны только потомки, но `analyze()`
каждый раз считает ещё и родителей — включая запросы в промежуточные таблицы, то есть в
неработающий код из п. 3.5.

**6.5. `getAllMetadata()` на первом обращении.** `DeletionService.php:82` заставляет
Doctrine разобрать метаданные **всех** сущностей проекта. Это заметная задержка первого
запроса, и любая поломанная конфигурация в неродственном модуле уронит `canDelete()`.

**6.6. Карта не переживает запрос.** Она статична — зависит только от кода, — но строится
заново в каждом процессе. Место ей в контейнере, собранной на этапе компиляции.

**6.7. Длинная транзакция.** Удаление большого дерева идёт одной транзакцией с массовыми
`DELETE`. На MySQL это долгие блокировки и риск упереться в таймаут. Нужны пачки и
ограничение объёма одной операции.

## 7. SOLID, PSR, Symfony

### SOLID

- **SRP.** `DeletionService` совмещает пять ролей: сбор карты, работа с метаданными,
  чтение значений рефлексией, разбор JSON и принятие решения. Отсюда и сложность
  тестирования (п. 2.9).
- **OCP.** Новый вид связи требует правки двух цепочек `elseif` (п. 2.7).
- **ISP.** Интерфейс наблюдателя требует шесть методов; реализации, которой нужны два,
  придётся написать четыре пустых. Плюс мёртвый `supports()`.
- **DIP.** Зависимость от конкретного `GenericReadRepository` вместо интерфейса — из-за
  этого в части 2 пришлось наследоваться от заглушки.
- **LSP** формально не нарушен, но фактически нарушен на прокси: подкласс ведёт себя не
  как базовый класс, потому что теряет атрибуты (п. 3.1).

### PSR

- **PSR-12.** После многострочного списка аргументов закрывающая скобка и открывающая
  фигурная должны стоять вместе — `) {`. Сейчас фигурная переносится
  (`DeletionService.php:24-26` и остальные конструкторы). Условие без фигурных скобок
  в `DeletionOrchestrator.php:150`. Сбитый отступ в `DeletionService.php:261`.
- **Аннотации типов.** `@return DependentGroupDto[]` у метода, возвращающего пару списков
  (`DeletionService.php:246`); в описании карты (`:17`) неверный тип последнего элемента;
  склеенные строки в docblock `OrderedPlanDto`. Такие аннотации хуже отсутствующих —
  они вводят в заблуждение и статический анализатор, и человека.
- **PSR-3.** Логирование есть только в одной реализации наблюдателя, а сам модуль не
  логирует ничего — включая проглоченные ошибки.

### Symfony

Это отдельная категория, и здесь расхождений с принятой практикой больше всего.

1. **Прямое внедрение `EntityManagerInterface` — и это здесь особенно чувствительно
   [проверено].** Модуль сам оборачивает работу в `wrapInTransaction()`, а тот при любой
   неудаче закрывает менеджер (`vendor/doctrine/orm/src/EntityManager.php:287-290`):

   ```php
   } finally {
       if (! $successful) {
           $this->close();
   ```

   Оба сервиса держат менеджер, полученный в конструкторе, поэтому после **первого же**
   неудачного удаления весь модуль остаётся нерабочим до конца процесса. В веб-запросе это
   ошибка 500, а в долгоживущем потребителе очереди — все последующие сообщения падают
   подряд. Принятый в Symfony подход — внедрять `ManagerRegistry` и уметь пересоздать
   менеджер (`resetManager()`) либо явно проверять `isOpen()`.

   Там же мелочь: `wrapInTransaction()` делает `flush()` сам (строка 281), а
   `DeletionOrchestrator.php:56` вызывает `flush()` ещё раз — второй вызов лишний.
2. **Карта должна собираться compiler pass'ом.** Тогда `getAllMetadata()` в рантайме не
   нужен вовсе, а ошибки конфигурации всплывают при сборке кэша, а не в проде (п. 2.1).
   Если карта всё же кэшируется — к ней нужен `CacheWarmerInterface`, чтобы первый
   запрос не платил за прогрев.
3. **`iterable $middlewares` без тегов и приоритетов.** Порядок наблюдателей сейчас —
   это порядок их регистрации в контейнере, то есть случайность. Для аудита и метрик
   порядок важен. Нужен тег (`#[AutoconfigureTag]`) и `!tagged_iterator` с `priority`.
4. **Вместо самодельных хуков — штатный `EventDispatcher`** с типизированными событиями
   и `#[AsEventListener]` (п. 2.6). Своя диспетчеризация через `method_exists` и
   `...$args` — это отказ от всего, что даёт фреймворк: типов, приоритетов, отладки через
   профайлер.
5. **Нет доменных исключений.** Модуль либо молчит, либо падает низкоуровневым
   `TypeError`. Нужна иерархия: `DeletionBlockedException`, `RelationMisconfiguredException`,
   `UnsupportedIdentifierException` — чтобы вызывающий код мог различать причины, а
   обработчик исключений — отвечать осмысленным кодом.
6. **Внутренние API не помечены.** `getChildRelationRules()` стоит либо убрать из
   публичного контракта, либо пометить `@internal`.
7. **DTO модуля отдаются прямо в `JsonResponse`** (пример в README). Внутренняя структура
   становится публичным контрактом API: изменение поля внутри модуля ломает клиентов.
   Нужен отдельный слой представления.
8. **Консольная команда** из README не приложена, но по описанию она принимает короткое
   имя класса и резолвит его — стоит проверить, что там нет неявного доверия вводу.

## 8. Что я сделал бы иначе

Если собирать модуль заново, я бы разложил его так:

```
Контракт модуля (только это видно снаружи)
    DeletionCheckerInterface::check(object): DeletionReport
    DeletionExecutorInterface::delete(object, DeletionOptions): DeletionResult

Метамодель — собирается на этапе компиляции
    #[OnDelete(RESTRICT|CASCADE|DETACH|IGNORE)]   ← на свойстве-ассоциации
    RelationRule (readonly VO)   ← политика + ссылка на маппинг Doctrine
    RelationMap                  ← неизменяемая, валидируется при сборке контейнера

Чтение (дёшево)
    DependencyProbe::exists(rule, id): bool        ← EXISTS, для решения
    DependencyProbe::sample(rule, id, limit): ids  ← только когда нужно показать
    DeletionChecker → DeletionReport { blocking[], willDelete[], willDetach[] }

Запись
    DeletionPlanner → PlanGraph (узлы, рёбра, глубина)
        ├ CycleDetector          ← явная ошибка вместо зависания
        └ TopologicalSorter      ← уровни удаления, тестируется без БД
    DeletionExecutor
        ├ сам проверяет DeletionChecker           ← инвариант внутри модуля
        ├ идёт по уровням снизу вверх, пачками
        └ возвращает DeletionResult (что и сколько)

Расширение
    RelationResolverInterface { ScalarFk | JoinTable | JsonArray | ... }

Наблюдение
    типизированные события через EventDispatcher
    некритичные слушатели — ошибки логируются, критичные — валят транзакцию
    обращения наружу — после коммита
```

Три принципа, которые я бы держал при этом:

1. **Отказ — в сторону запрета.** Не смогли достоверно определить связи — отказываем и
   говорим почему. Ошибка конфигурации — красная сборка, а не тихое разрешение.
2. **Doctrine знает структуру, атрибут задаёт политику.** Никакого дублирования маппинга
   руками — ни имён полей, ни таблиц, ни колонок.
3. **Решение принимается один раз и принадлежит исполнителю.** Нельзя, чтобы инвариант
   держался на дисциплине вызывающего кода.

Порядок работ, если нужно чинить существующий модуль без переписывания:

| Очередь | Что | Почему сначала |
|---|---|---|
| 1 | Резолв реального класса в одном месте (п. 3.1) | одна строка, закрывает молчаливое удаление данных |
| 2 | Проверка `canDelete` в `execute()` (п. 3.2) | инвариант, тоже несколько строк |
| 3 | `visited` в обходе (п. 3.3) | защита от зависания |
| 4 | Топологическая сортировка (п. 3.4) | целостность данных |
| 5 | Определиться с семантикой `BLOCKING` и зафиксировать тестом (п. 4.1) | без этого остальное чинить бессмысленно |
| 6 | `EXISTS` вместо материализации (п. 6.1) | снимает основную нагрузку |
| 7 | Валидация карты при сборке (п. 2.1) | закрывает целый класс молчаливых отказов |

## 9. Часть 2 — тесты

Выбран вариант A. Тесты: `tests/DeletionServiceTest.php`, 12 штук.

Разделены на две группы:

- **Зафиксированное поведение** — то, что работает верно и должно быть защищено от
  регрессий: блокирующий потомок запрещает удаление, `DETACH_RELATIONS` не запрещает,
  `DELETE_CHILD` попадает в список на удаление, счётчик совпадает с числом
  идентификаторов.
- **Найденные дефекты** — воспроизводят проблемы из ревью: прокси и потеря связи,
  объявленной на базовом классе (3.1), потеря `REFERENCE`+`NONE` (4.3), недостижимая
  проверка родителей (4.2), неоднозначный `hard` (4.4), `TypeError` на поле-ассоциации
  (5.1), неинициализированное свойство (5.2).
  Они зелёные, потому что проверяют **фактическое** поведение; в каждом указано, каким оно
  должно быть. После исправлений эти тесты станут красными — это и есть сигнал переписать
  их под правильное поведение.

Запуск:

./vendor/bin/phpunit
```

```

Одно предупреждение об устаревшем `setAccessible()` приходит из самого модуля (п. 5.7).

Оговорка: `Shared\Persistence\GenericReadRepository` в архив не входит, а
`DeletionService` типизирует его в конструкторе — без него код не загружается. Поэтому
