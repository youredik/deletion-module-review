# Code Review: модуль `Deletion`

Эдуард Сарваров · для 3snet

Смотрел на PHP 8.5, Doctrine ORM 2.19 и 3.6.7, PHPUnit 13.

## Главное

Задумано верно: связи описаны прямо у сущностей, отдельно разведены «удалить потомка» и
«разорвать связь», есть режим примерки и общая транзакция.

Но есть проблема важнее всех остальных: **если в настройке связей ошибка, модуль
разрешает удаление, а не запрещает.** Для защиты это работает наоборот, чем должно.

| Что | Чем обернётся |
|---|---|
| Любая ошибка в настройке разрешает удаление | защита не срабатывает, и никто не узнает |
| Прокси Doctrine теряет все связи | `canDelete = true`, хотя потомки на месте |
| `execute()` не смотрит на `canDelete` | удаляет в обход собственной проверки |
| Рекурсия не помнит, где была | зациклится и повесит процесс |
| «Упорядоченный план» без сортировки | нарушение внешних ключей |
| Ветка many-to-many не работает | падает при каждом вызове |
| README и код понимают `BLOCKING` наоборот | связи размечают не тем, чем они работают |

**Что хорошо.** Правило написано рядом с сущностью, а не спрятано в конфиге. Разделены
«удалить потомка» и «оставить потомка, убрать связь» — про это обычно вспоминают поздно и
больно. Сразу есть режим примерки и точки расширения, код аккуратный: `strict_types`,
`final`, `readonly`, enum вместо строк.

## Архитектура

### Ошиблись в настройке — и удаление разрешено

| Что пошло не так | Что ответит `canDelete()` |
|---|---|
| Объект пришёл как прокси | `true`, зависимостей нет |
| `RelationTo` написан на абстрактном предке | `true`, наследники его не видят |
| Опечатка в имени класса или поля | `true`, связи будто и нет |
| `REFERENCE` вместе с `cascade: NONE` | `true`, группа пропадает из ответа |
| Упал middleware | ошибку проглотили, удаление пошло дальше |

Ни в одном случае модуль не ругается — просто разрешает удалить. Защита должна вести себя
наоборот: не может ответить точно, пусть запрещает и говорит почему. Чинить по одному месту
бесполезно, проверку надо перенести раньше: пусть карта связей собирается и проверяется при
сборке контейнера. Тогда опечатка — красная сборка, а не молча разрешённое удаление в проде.

### Модуль описывает связи заново, хотя Doctrine их уже знает

В атрибуте надо руками указать класс, поле, промежуточную таблицу и обе её колонки. Всё
это уже лежит в маппинге (`labels type=8 target=Label joinTable=product_label`). Из-за
этого описание разъезжается с маппингом, промежуточную таблицу приходится обрабатывать
вручную, значения читаются самодельной рефлексией, и появляется беда с прокси.

Границу лучше провести так: **структуру связей знает Doctrine, атрибут говорит только что
делать при удалении** — и вешать его на само свойство:

```php
#[OnDelete(OnDelete::RESTRICT)]
private OrderEntity $order;
```

Опечатка в имени поля тут невозможна, потому что имени поля больше нет.

### Проверка есть, но удаление её не спрашивает

`analyze()` считает `canDelete`. `execute()` (`Orchestrator:30`) получает тот же объект и
на это поле не смотрит — сразу строит план и удаляет.

Дело не в забытой строчке: за это правило никто не отвечает — один считает, второй должен
бы соблюсти, но не обязан. Проверять запрет должен тот, кто удаляет.

### План удаления — это просто два массива

В `OrderedPlanDto` два плоских списка: ни узлов, ни связей между ними, ни уровней —
сортировать нечего. Поэтому удаление идёт в том порядке, в каком классы попали в массив.
Нужен граф: с ним сортировка станет отдельной частью, которую можно проверить без базы.

### Проверить «можно ли удалить» стоит столько же, сколько удалить

`canDelete()` зовут из контроллера, ему хватило бы `EXISTS`; `execute()` нужны
идентификаторы. Сейчас оба идут через одну функцию, которая грузит зависимые сущности
целиком.

### Middleware здесь не middleware

```php
if (method_exists($mw, $method)) {
    try { $mw->{$method}(...$args); } catch (Throwable) {}
}
```

Типы не проверяются, обернуть операцию целиком нельзя, прервать нельзя, `supports()`
объявлен и не вызывается ни разу. Всё работает внутри транзакции, поэтому любой поход по
сети держит её открытой. Стоит выбрать одно: настоящую цепочку, как в Messenger, или
события через `EventDispatcher`.

### Новый вид связи придётся вписывать в два места

Виды связей разбираются цепочкой `if/elseif`, и таких цепочек две. Лучше
`RelationResolverInterface` под скаляр, промежуточную таблицу и JSON: тогда новый вид это
новый класс.

### Непонятно, зачем модуль, если есть внешние ключи

`ON DELETE RESTRICT` не даст удалить строку с потомками надёжнее, чем любой PHP. Модуль
нужен для другого: заранее объяснить, что именно мешает, показать план и описать правила
там, где внешнего ключа нет — например, для связи через JSON. Значит и роли стоит развести:
**гарантию даёт база, модуль объясняет.** Тогда предыдущая проблема не смертельна — модуль
ошибётся, база не даст. А если внешних ключей нет и вся надежда на модуль, любая опечатка
в атрибуте однажды сотрёт данные.

## Что сломано

**Прокси теряет все связи.** `DeletionService:113` и `:252` берут класс через
`$object::class`. У прокси это `Proxies\__CG__\App\Entity\Order`, а карта построена по
настоящим именам. Причина глубже: прокси — это подкласс, а атрибуты в PHP не наследуются.

| Как загружен объект | `$obj::class` | видно атрибутов |
|---|---|---|
| Обычный прокси (ORM 2.x) | `Proxies\__CG__\...` | 0 |
| Нативный ленивый объект (PHP 8.4, ORM 3.4+) | настоящий класс | все |

Получается, на вашей версии проблема есть, а после обновления ORM она пропадёт сама — то
есть защита данных зависит от настроек ORM. Класс лучше определять явно и в одном месте:
`$this->em->getClassMetadata($object::class)->getName()`. `ClassUtils::getRealClass()` не
берите, в ORM 3 его удалили.

У этого же корня есть вторая беда, которую новые версии не исправят: `RelationTo` на
абстрактном предке наследники не увидят. При наследовании таблиц связь просто исчезает.

**`execute()` не проверяет `canDelete`.** Нужна проверка внутри и своё исключение, плюс
явный `force`, если обойти запрет надо осознанно.

**Рекурсия зацикливается.** `Orchestrator:111-140` идёт по потомкам, не запоминая, где уже
был. Связь `A → B → A` или дерево категорий уводят в бесконечность, а узел, до которого
ведут два пути, обходится дважды. Достаточно запоминать пары «класс + идентификатор».

**Порядок удаления неверный.** `Orchestrator:76` раскладывает карту в порядке, в каком туда
попали классы, а попадают они сверху вниз. Значит, родительские строки удаляются раньше
дочерних.

**Many-to-many для родителей не работает.** `DeletionService:215-222` собирает DQL, но в
`FROM` подставляет имя таблицы: `[Semantical Error] near 'order_tag jt': Class 'order_tag'
is not defined.` Падает всегда — значит, этой веткой никогда не пользовались. Нужен обычный
SQL через DBAL, как уже сделано в `detachJoinRow()`.

**`deleteByIds()` путает идентификаторы.** `Orchestrator:113-115`: если ключ называется не
`id`, берётся `$group->field` — а это поле связи на родителя, тогда как в `$group->ids`
лежат идентификаторы потомков. В итоге выполняется `DELETE ... WHERE e.order_id IN
(:childIds)` и удаляются не те строки. Составные ключи не поддержаны вовсе (`:93` берёт
только первый).

**Ошибки наблюдателей пропадают.** `Orchestrator:162` — пустой `catch`. Запись в аудит
может упасть, а удаление всё равно пройдёт. Тем, без кого нельзя, надо давать ронять
транзакцию, остальных — хотя бы логировать.

## Что написано не так, как работает

**README и код понимают связь наоборот.** В README: «`OrderItemEntity` нельзя удалить, если
она связана с `OrderEntity`». В коде (`:120-122`): «BLOCKING означает нельзя удалить
РОДИТЕЛЯ». Работает второе. Разработчик размечает по документации и получает не ту защиту,
на которую рассчитывал. Мне ближе то, что в коде — это обычный `RESTRICT`. Тогда надо
поправить README и заодно название: `BLOCKING` → `RESTRICT_PARENT`, чтобы направление было
видно сразу.

**Проверка блокирующих родителей не сработает никогда.** В `:122` жёстко стоит
`$isBlocking = false`, поэтому цикл в `analyze():47-52` вхолостую. Запросы ради него при
этом выполняются.

**`hard` не значит «блокирует».** `canDelete()` склеивает три списка в один. У detach-группы
`hard` бывает `true`, хотя удалять можно, а у родительских он всегда `false`. README
предлагает печатать по этому флагу «блокирует удаление» — надпись будет врать. Наружу лучше
отдавать три отдельных списка: `blocking`, `willDelete`, `willDetach`.

И ещё: README описывает атрибут `DependsOn` с параметром `parent`, а в коде `RelationTo` с
`entity`. Параметр `cascade`, который всем и управляет, не описан вообще.

## Что не учтено

- **Обычная связь роняет проверку.** `getScalarFkValue()` (`:227-239`) обещает вернуть
  `int|string|null`, но читает свойство как есть. Для `private OrderEntity $order` — это
  ровно пример из README — вернётся объект и вылетит `TypeError`. Идентификатор надо брать
  через `getIdentifierValues()`. Там же нет `isInitialized()`, поэтому незаполненное
  свойство тоже роняет проверку.
- **Удаление идёт мимо Doctrine.** DQL `DELETE` не вызывает `preRemove`/`postRemove` и не
  чистит identity map. Если на этих событиях висит удаление файлов или переиндексация, они
  не отработают. Строки в промежуточных таблицах у удалённых потомков остаются висеть.
- **`IN (...)` без разбивки** упрётся в лимит параметров. И между `plan()` и `DELETE` может
  появиться новая блокирующая запись — корень стоит блокировать в той же транзакции.
- **`isJsonField()` лезет к метаданным по-старому.** На ORM 3.6 `fieldMappings` — это уже
  объект, но обращение как к массиву работает, так что ничего не сломается. Всё же
  правильнее `getTypeOfField() === Types::JSON`. А ветка с `options['json']` смотрит на
  опцию, которой у Doctrine нет.
- **По мелочи:** `setAccessible()` устарел в PHP 8.5 (`:180`, `:235`); `array_filter()`
  (`:198`) оставляет старые ключи, и в JSON вместо массива уедет объект; имена таблиц
  подставляются в SQL без экранирования (`Orchestrator:172`); наружу отдаются `ids` без
  проверки, чьи это записи.

## Что будет тормозить

- **Объекты грузятся целиком ради счётчика** (`:260-281`). Чтобы узнать количество и взять
  идентификаторы, поднимаются полноценные сущности: у родителя со 100 тысячами потомков это
  100 тысяч объектов в памяти на каждый вызов. Для ответа хватит `EXISTS` — база
  остановится на первой же строке, а примеры идентификаторов можно взять отдельным запросом
  с `LIMIT`.
- **N+1 в рекурсии** (`:128`): на каждый идентификатор свой `find()`, а на каждого потомка
  снова `analyze()`, который опять идёт в базу — и считает ещё родителей, хотя нужны только
  потомки.
- **Нужны индексы, но об этом нигде не сказано.** Без индекса на `child.parent_id` каждая
  проверка превращается в полный проход по таблице.
- **`getAllMetadata()`** заставляет Doctrine разобрать все сущности проекта: сломанный
  маппинг в чужом модуле уронит `canDelete()`. Карта зависит только от кода — ей место в
  контейнере.
- **Долгая транзакция** с массовыми `DELETE` — блокировки и риск таймаута на MySQL.

## SOLID, PSR, Symfony

**SOLID.** SRP — `DeletionService` делает сразу всё: собирает карту, читает метаданные,
лезет рефлексией, разбирает JSON и принимает решение. OCP — новый вид связи требует правки
двух цепочек. ISP — у наблюдателя шесть обязательных методов, из них `supports()` вообще не
вызывается. DIP — в конструкторе конкретный `GenericReadRepository`, поэтому его нечем
подменить в тестах.

**PSR-12.** После многострочного списка аргументов `)` и `{` должны стоять на одной строке
(`:24-26` и другие конструкторы). Условие без фигурных скобок (`Orchestrator:150`). Сбитый
отступ (`:261`). У метода, который возвращает пару списков, стоит `@return
DependentGroupDto[]` (`:246`) — такая подсказка хуже, чем никакой.

**Symfony.**

- **`EntityManagerInterface` внедряется напрямую**, а `wrapInTransaction()` при неудаче
  закрывает менеджер (`EntityManager.php:287-290`). После первого же неудачного удаления
  модуль не работает до конца процесса — в обработчике очереди посыпется всё подряд. Лучше
  `ManagerRegistry`, чтобы менеджер можно было пересоздать.
- **Карту стоит собирать compiler pass'ом** — тогда ошибки в настройке вылезут при сборке
  кэша, а не в проде.
- **`iterable $middlewares` без тегов и приоритетов** — порядок сейчас какой получится.
  Сегодня это делают через `#[AutowireIterator]` на аргументе и `#[AsTaggedItem(priority:
  ...)]` на самой реализации; старый способ с `getDefaultPriority()` в 8.1 объявлен
  устаревшим и уйдёт в 9.0.
- **Нет своих исключений** — модуль либо молчит, либо падает `TypeError`.
- **`getChildRelationRules()`** отдаёт наружу внутренние массивы, а DTO уезжают прямо в
  `JsonResponse`, и внутреннее устройство становится контрактом API. Заодно:
  `wrapInTransaction()` сам делает `flush()`, а `Orchestrator:56` вызывает его ещё раз.

## Как бы я сделал

```
Снаружи      check(object): DeletionReport | delete(object, options): DeletionResult
Описание     #[OnDelete(...)] на свойстве: только политика, структура из Doctrine;
             карта собирается и проверяется при сборке
Чтение       exists() — для ответа «можно ли»; sample() — идентификаторы для показа
Запись       Planner: граф, поиск циклов, топологическая сортировка;
             Executor сам проверяет запрет, идёт снизу вверх пачками, отдаёт отчёт
Расширение   RelationResolver: скаляр | промежуточная таблица | JSON
События      типизированные; без кого нельзя — валит транзакцию, остальные логируются;
             наружу обращаемся после коммита
```

Если коротко, то так: **сомневаешься — запрещай**; **структуру знает Doctrine, атрибут
задаёт только политику**; **проверять запрет должен тот, кто удаляет.**

Чинить, не переписывая, я бы стал в таком порядке: определять реальный класс в одном месте
→ проверять запрет внутри `execute()` → запоминать пройденные узлы → отсортировать план →
договориться, что значит `BLOCKING` → перейти на `EXISTS` → проверять карту при сборке.
Первые три — по несколько строк, а закрывают потерю данных и зависание.

## Часть 2 — тесты

Вариант A. `tests/DeletionServiceTest.php`, 12 тестов, две группы.

Первая — то, что работает верно и должно таким остаться. Вторая повторяет найденные
проблемы: прокси, связь с абстрактного предка, потерю `REFERENCE` + `NONE`, вхолостую
работающую проверку родителей, неоднозначный `hard`, `TypeError` на обычной связи,
незаполненное свойство. Тесты зелёные, потому что проверяют, как есть сейчас; в каждом
написано, как должно быть. Почините — покраснеют, и это будет сигналом переписать их.

`GenericReadRepository` в архив не попал, а `DeletionService` требует его в конструкторе —
рядом лежит заглушка, собранная по вызовам, тестовый двойник наследуется от неё.
