# Code Review: модуль `Deletion`

Эдуард Сарваров · для 3snet

Проверял на PHP 8.5, Doctrine ORM 2.19 и 3.6.7, PHPUnit 13.

## Главное

Идея правильная: связи описаны рядом с сущностями, разведены «удалить потомка» и
«разорвать связь», есть dry-run и общая транзакция. Но одно свойство перевешивает
остальное: **при любой ошибке конфигурации модуль разрешает удаление, а не запрещает.**
Для компонента, который должен не дать удалить лишнее, это перевёрнутый выбор по умолчанию.

| Что | Последствие |
|---|---|
| Все режимы отказа разрешают удаление | защита не срабатывает молча |
| Прокси Doctrine теряет все связи | `canDelete = true` при живых блокирующих потомках |
| `execute()` не смотрит на `canDelete` | удаление в обход собственной проверки |
| Рекурсия без защиты от циклов | зависание процесса |
| «Упорядоченный план» без сортировки | нарушение внешних ключей |
| Ветка many-to-many не работает | исключение на каждом вызове |
| README и код трактуют `BLOCKING` наоборот | связи размечают не тем, чем они работают |

**Что хорошо:** декларативность — правило живёт рядом с сущностью; разделение
`DELETE_CHILD` и `DETACH_RELATIONS` (о нём обычно вспоминают поздно и дорого); dry-run и
точки расширения заложены сразу; `strict_types`, `final`, `readonly`, enum вместо строк.

## Архитектура

### Отказ в сторону разрешения

| Что пошло не так | Ответ `canDelete()` |
|---|---|
| Объект пришёл как прокси | `true`, зависимостей нет |
| `RelationTo` на абстрактном предке | `true`, наследники его не видят |
| Опечатка в классе или поле | `true`, связи просто нет |
| `REFERENCE` + `cascade: NONE` | `true`, группа исчезает из ответа |
| Упал middleware | ошибка проглочена, удаление идёт дальше |

Ни один случай не даёт ошибки — все дают разрешение, молча. Страж должен вести себя
наоборот: не может достоверно ответить — отказывает и жалуется. Лечится переносом проверок
на сборку: карта строится и валидируется при компиляции контейнера, тогда опечатка — это
красная сборка, а не тихо разрешённое удаление.

### Метамодель дублирует то, что Doctrine уже знает

Атрибут требует руками указать целевой класс, поле, промежуточную таблицу и обе колонки —
всё это уже лежит в маппинге (`labels type=8 target=Label joinTable=product_label`).
Отсюда растут рассинхрон с маппингом, ручная работа с промежуточной таблицей, самодельная
рефлексия и проблема с прокси.

Правильная граница — **Doctrine отвечает за структуру, атрибут за политику**, и вешается
на само свойство:

```php
#[OnDelete(OnDelete::RESTRICT)]
private OrderEntity $order;
```

Опечатка в имени поля становится невозможной, потому что имени поля больше нет.

### Решение принимается в двух местах и разошлось

`analyze()` вычисляет `canDelete`; `execute()` (`Orchestrator:30`) получает тот же объект и
не смотрит на это поле. Это не пропущенная строчка, а следствие того, что политика
размазана между тем, кто решает, и тем, кто обязан соблюсти, но не обязан по контракту.
Инвариант должен принадлежать исполнителю.

### План удаления не смоделирован

`OrderedPlanDto` — два плоских массива. Ни узлов, ни рёбер, ни глубины: сортировать нечего,
поэтому порядок получается тем, в котором классы попали в массив. Нужны `PlanNode` и
`PlanEdge` — тогда топологическая сортировка станет отдельным компонентом, тестируемым без
базы.

### Чтение и запись не разделены

`canDelete()` — запрос из контроллера, ему хватило бы `EXISTS`. `execute()` — команда, ей
нужны идентификаторы. Обе стороны ходят через одну функцию, которая материализует все
зависимые сущности целиком.

### То, что названо middleware, устроено как хуки

```php
if (method_exists($mw, $method)) {
    try { $mw->{$method}(...$args); } catch (Throwable) {}
}
```

Типов нет, обернуть операцию нельзя, прервать нельзя, `supports()` объявлен и не
вызывается ни разу, всё выполняется внутри транзакции. Нужно выбрать одно: цепочку как в
Messenger либо типизированные события через `EventDispatcher`.

### Расширяемость закрыта

Виды связей разбираются цепочкой `if/elseif` в двух местах — новый вид требует правки
обеих. Просится `RelationResolverInterface` под скаляр, промежуточную таблицу и JSON.

### Не определено, чем модуль дополняет внешние ключи

`ON DELETE RESTRICT` не даст удалить строку с потомками надёжнее любого PHP. Модуль нужен
ради другого: объяснить заранее, что мешает, показать план и описать правила там, где
внешнего ключа нет — например, связь через JSON. Отсюда разделение, которого нет:
**гарантию даёт база, модуль даёт объяснение.** Тогда отказ в сторону разрешения не
катастрофа. Если же внешних ключей нет и модуль считается единственной защитой, каждая
опечатка в атрибуте — тихая потеря данных.

## Критичные дефекты

**Прокси теряет все связи.** `DeletionService:113` и `:252` берут класс через
`$object::class`. У прокси это `Proxies\__CG__\App\Entity\Order`, а карта построена по
настоящим именам. Причина глубже: прокси — подкласс, а атрибуты в PHP не наследуются.

| Режим | `$obj::class` | атрибутов видно |
|---|---|---|
| Классический прокси (ORM 2.x) | `Proxies\__CG__\...` | 0 |
| Нативный ленивый объект (PHP 8.4, ORM 3.4+) | настоящий класс | все |

Баг живёт на вашем стеке и исчезнет при обновлении ORM сам — то есть поведение защиты
данных зависит от настройки ORM. Определять класс надо явно и в одном месте:
`$this->em->getClassMetadata($object::class)->getName()`; `ClassUtils::getRealClass()` не
использовать, в ORM 3 он удалён. Тот же корень даёт вторую проблему, которую нативные
объекты не лечат: `RelationTo` на абстрактной базовой сущности наследники не увидят — при
наследовании таблиц связь просто перестаёт существовать.

**`execute()` не проверяет `canDelete`.** Нужна проверка внутри с доменным исключением и
явным `force` для осознанного обхода.

**Бесконечная рекурсия.** `Orchestrator:111-140` спускается по потомкам без множества
посещённых: цикл `A → B → A` или дерево категорий уводят в бесконечность, а узел,
достижимый двумя путями, обходится повторно. Нужен `visited` по паре «класс + идентификатор».

**План не упорядочен.** `Orchestrator:76` разворачивает карту в порядке добавления классов,
а добавляются они сверху вниз — родительские строки удаляются раньше дочерних.

**Many-to-many для родителей не работает.** `DeletionService:215-222` строит DQL, но в
`FROM` подставляет имя таблицы: `[Semantical Error] near 'order_tag jt': Class 'order_tag'
is not defined.` Падает всегда — путь никогда не выполнялся. Нужен нативный SQL через DBAL,
как уже сделано в `detachJoinRow()`.

**`deleteByIds()` смешивает идентификаторы.** `Orchestrator:113-115`: если ключ не `id`,
берётся `$group->field` — поле связи на родителя, тогда как `$group->ids` это
идентификаторы потомков. Выполняется `DELETE ... WHERE e.order_id IN (:childIds)` — удалятся
не те строки. Составные ключи не поддержаны (`:93` берёт только первый).

**Ошибки наблюдателей исчезают.** `Orchestrator:162` — пустой `catch`: аудит удаления может
упасть, а удаление пройдёт. Критичные наблюдатели должны валить транзакцию, некритичные —
логироваться.

## Семантика

**README и код описывают связь наоборот.** README: «`OrderItemEntity` нельзя удалить, если
она связана с `OrderEntity`». Код (`:120-122`): «BLOCKING означает нельзя удалить
РОДИТЕЛЯ». Реализовано второе — разработчик размечает по документации и получает не ту
защиту. Мне ближе вариант из кода, это обычный `RESTRICT`; тогда править README и имя:
`BLOCKING` → `RESTRICT_PARENT`, чтобы направление читалось из названия.

**Проверка блокирующих родителей недостижима.** `:122` жёстко ставит `$isBlocking = false`,
поэтому цикл в `analyze():47-52` не сработает никогда — а запросы ради этих групп
выполняются.

**`hard` не означает «блокирует».** `canDelete()` склеивает три списка: у detach-группы
`hard` бывает `true` при разрешённом удалении, у родительских всегда `false`. README
предлагает печатать по нему «блокирует удаление» — надпись будет неверной. Нужен
структурированный ответ: `blocking` / `willDelete` / `willDetach`.

Плюс README описывает несуществующий атрибут `DependsOn` с параметром `parent` — в коде
`RelationTo` с `entity`, а `cascade` не описан вовсе.

## Краевые случаи

- **Поле-ассоциация роняет проверку.** `getScalarFkValue()` (`:227-239`) объявлен
  `int|string|null`, но читает свойство как есть: для `private OrderEntity $order` — ровно
  примера из README — вернётся объект и вылетит `TypeError`. Идентификатор надо брать через
  `getIdentifierValues()`. Там же нет `isInitialized()`, поэтому неинициализированное
  типизированное свойство тоже роняет проверку.
- **Массовое удаление мимо UnitOfWork.** DQL `DELETE` не запускает `preRemove`/`postRemove`
  и не чистит identity map: если на событиях висит удаление файлов или переиндексация — она
  не отработает. Строки промежуточных таблиц у каскадно удалённых потомков остаются
  сиротами.
- **`IN (...)` без пачек** — упор в лимит параметров; **гонка между `plan()` и `DELETE`** —
  может появиться новая блокирующая запись, нужна блокировка корня в той же транзакции.
- **`isJsonField()` на устаревшей форме доступа.** На ORM 3.6 `fieldMappings` это объект
  `FieldMapping`, но массивный доступ работает — код не сломается. Штатный способ всё же
  `getTypeOfField() === Types::JSON`. Ветка `options['json']` опирается на опцию, которой
  нет среди стандартных.
- **Мелочи:** `setAccessible()` устарел в PHP 8.5 (`:180`, `:235`); `array_filter()` (`:198`)
  сохраняет ключи, и при сериализации вместо массива уедет объект; имена таблиц
  подставляются в SQL без `quoteIdentifier()` (`Orchestrator:172`); наружу отдаются `ids`
  без ограничения по владельцу.

## Производительность

- **Полная материализация ради счётчика** (`:260-281`): грузятся целые объекты, чтобы взять
  идентификаторы и посчитать количество — у родителя со 100 тысячами потомков это 100 тысяч
  объектов в памяти на каждый вызов. Хватает `EXISTS`: база останавливается на первой
  строке. Примеры идентификаторов — отдельным запросом с `LIMIT`.
- **N+1 в рекурсии** (`:128`): `find()` на каждый идентификатор, и на каждого потомка снова
  `analyze()`, который снова ходит в базу — причём считает и родителей, хотя оркестратору
  нужны только потомки.
- **Скрытое требование к индексам**: без индекса на `child.parent_id` каждая проверка это
  полное сканирование.
- **`getAllMetadata()`** разбирает метаданные всех сущностей проекта — поломанная
  конфигурация в чужом модуле уронит `canDelete()`. Карта зависит только от кода, ей место
  в контейнере.
- **Длинная транзакция** с массовыми `DELETE` — блокировки и риск таймаута на MySQL.

## SOLID, PSR, Symfony

**SOLID.** SRP — `DeletionService` совмещает сбор карты, метаданные, рефлексию, разбор JSON
и принятие решения. OCP — новый вид связи требует правки двух цепочек. ISP — шесть
обязательных методов у наблюдателя плюс мёртвый `supports()`. DIP — зависимость от
конкретного `GenericReadRepository`, из-за неё модуль нечем подменить в тестах.

**PSR-12.** После многострочного списка аргументов `)` и `{` должны стоять вместе (`:24-26`
и остальные конструкторы); условие без скобок (`Orchestrator:150`); сбитый отступ (`:261`);
неверный `@return DependentGroupDto[]` у метода, возвращающего пару списков (`:246`) —
такая аннотация хуже отсутствующей.

**Symfony.**

- **`EntityManagerInterface` внедряется напрямую**, а `wrapInTransaction()` при неудаче
  закрывает менеджер (`EntityManager.php:287-290`). После первого же неудачного удаления
  модуль нерабочий до конца процесса — в потребителе очереди это лавина падений. Нужен
  `ManagerRegistry`.
- **Карта должна собираться compiler pass'ом** — тогда ошибки конфигурации всплывают при
  сборке кэша.
- **`iterable $middlewares` без тегов и приоритетов** — порядок случаен. Актуально:
  `#[AutowireIterator]` на аргументе и `#[AsTaggedItem(priority: ...)]` на реализации;
  старый способ через `getDefaultPriority()` устарел в 8.1 и удаляется в 9.0.
- **Нет доменных исключений** — модуль либо молчит, либо падает `TypeError`.
- **`getChildRelationRules()`** отдаёт наружу внутренние кортежи, а DTO уезжают прямо в
  `JsonResponse` — внутренняя структура становится контрактом API. И `wrapInTransaction()`
  делает `flush()` сам, а `Orchestrator:56` вызывает его ещё раз.

## Что сделал бы иначе

```
Контракт     check(object): DeletionReport | delete(object, options): DeletionResult
Метамодель   #[OnDelete(...)] на свойстве; политика + ссылка на маппинг Doctrine;
             карта собирается и валидируется на этапе компиляции
Чтение       exists() — EXISTS для решения; sample() — идентификаторы для показа
Запись       Planner → граф + поиск циклов + топологическая сортировка;
             Executor сам проверяет запрет, идёт снизу вверх пачками, отдаёт отчёт
Расширение   RelationResolver: скаляр | промежуточная таблица | JSON
Наблюдение   типизированные события; критичные валят транзакцию, остальные
             логируются; обращения наружу — после коммита
```

Три принципа: **отказ в сторону запрета**; **Doctrine знает структуру, атрибут задаёт
политику**; **решение принимается один раз и принадлежит исполнителю.**

Если чинить без переписывания, порядок такой: резолв реального класса в одном месте →
проверка запрета внутри `execute()` → `visited` в обходе → топологическая сортировка →
определиться с семантикой `BLOCKING` → `EXISTS` вместо материализации → валидация карты
при сборке. Первые три — несколько строк каждая, а закрывают молчаливое удаление данных и
зависание.

## Часть 2 — тесты

Вариант A. `tests/DeletionServiceTest.php`, 12 тестов, две группы. Первая — поведение,
которое работает верно и должно быть защищено от регрессий. Вторая воспроизводит найденные
дефекты: прокси, связь с базового класса, потерю `REFERENCE`+`NONE`, недостижимую проверку
родителей, неоднозначный `hard`, `TypeError` на ассоциации, неинициализированное свойство.
Они зелёные, потому что проверяют фактическое поведение; в каждом указано, каким оно должно
быть. После исправлений станут красными — это и есть сигнал переписать их.

`GenericReadRepository` в архив не входит, а `DeletionService` типизирует его в
конструкторе — рядом лежит заглушка по вызовам, тестовый двойник наследуется от неё.
